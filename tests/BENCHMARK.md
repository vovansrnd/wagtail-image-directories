# Benchmark: скан ссылок на объёме 10 000 страниц + 2 001 ревизия

Инструмент: `tests/bench_reference_scan.py` (env `BENCH_PAGES`, `BENCH_REVISION_PAGES`).
Окружение прогона: **Python 3.14.4, Django 6.0.9, Wagtail 8.1, PostgreSQL 14.15
(сервер; тестовая БД — PostgreSQL, host 127.0.0.1), psycopg2 2.9.13**, пакет
установлен из wheel (site-packages-импорт).

## Фактический вывод (Wagtail 8.1 / Django 6.0.9 / PostgreSQL)

```
создано 10000 страниц + 2000 ревизий за 602.1s
СКАН (текущий контент + все ревизии): 3.73s; просмотрено записей:
  current_content_values_scanned = 88018, revision_records_scanned = 2001
find_referenced_images: 1721.0 ms; ссылок на bench-изображение: 9003
ИТОГ: 10000 страниц, 2000 ревизий: скан 3.73s, память пик 6.8 MB
```

## Уточнение метрик (важно)

- **3.73 s** — `scan_content_and_revision_references` **с включённым
  `tracemalloc`** (отслеживание аллокаций замедляет выполнение);
- **1.7 s** — `find_referenced_images` **без tracemalloc** (после его
  остановки). Замеры НЕ полностью сопоставимы — сравнивать напрямую нельзя;
- **6.8 MB** — **пик Python-аллокаций, отслеженных tracemalloc**. Это НЕ RSS
  процесса и НЕ память PostgreSQL;
- просмотрено записей: **88 018 значений текущего контента** + **2 001 запись
  ревизий** (счётчики сканера).

## Интерпретация

Скан линеен по объёму контента и выполняется ОДИН раз на батч (удаление/
перенос). На масштабе 10k страниц + 2k ревизий — секунды, не минуты.
Ориентир для продакшн-объёмов требует отдельного прогона на реальных данных;
для релизного решения 0.2.2 зафиксированного масштаба достаточно.
